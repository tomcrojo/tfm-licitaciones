Plataforma DataOps reproducible

De datos abiertos a oportunidades trazables

Integración y explotación de licitaciones públicas
Caso de estudio: contratación tecnológica
Vídeo · 5 minutos
La contratación pública publica una enorme cantidad de información, pero está repartida entre fuentes y formatos distintos. Mi TFM aborda ese problema desde la ingeniería de datos: he construido un prototipo reproducible que transforma datos oficiales de licitaciones en productos analíticos trazables. En cinco minutos explicaré el problema, la arquitectura, las decisiones técnicas y qué he podido demostrar realmente.

01 · El problema

Publicar no significa que los datos estén listos para analizar

FUENTES

TED + OpenPLACSP

Ámbitos, frecuencias y semánticas diferentes.

FORMATOS

JSON · ZIP · Atom · XML

Parsing específico sin perder el origen oficial.

HISTORIA

Revisiones + anulaciones

Una actualización no puede borrar la evidencia anterior.

Las dos fuentes principales son TED, para avisos europeos, y OpenPLACSP, para licitaciones españolas. No ofrecen el mismo formato ni la misma semántica: hay JSON, ZIP, Atom y XML CODICE; también revisiones, anulaciones y campos incompletos. Descargar datos no basta. Para analizarlos con rigor hay que conservar el origen, contabilizar rechazos, separar fechas que significan cosas distintas y evitar que una nueva versión destruya la evidencia anterior.

02 · Objetivo y aportación

Una cadena de datos auditable, no una caja negra de clasificación.

El caso tecnológico guía la demostración; el contrato canónico y CPV mantienen el sistema generalista.

reproducibletrazabletipadosector-agnosticoffline-testable
El objetivo ha sido diseñar una plataforma DataOps local, reproducible y generalista. Aunque el caso de estudio de la memoria son las licitaciones tecnológicas, el modelo se apoya en CPV, la taxonomía oficial, y no está limitado a un único sector. La aportación principal no es un clasificador sofisticado: es una cadena de datos auditable, con contratos estables, procedencia y decisiones que pueden volver a ejecutarse y revisarse.

03 · Arquitectura implementada

Cada capa responde una pregunta distinta

RAWPayload, checksum y recuperación
BRONZEParsing, rechazos y tombstones
SILVERHistórico canónico de eventos
GOLDEstado vigente y oportunidades
DUCKDBVistas SQL versionadas
TABLEAUCSV deterministas

Python ingiere y parsea · Polars transforma · PySpark resuelve estado y Gold · DuckDB sirve analítica

El flujo comienza en Raw, donde se conserva el payload oficial junto con su checksum y el instante de recuperación. Bronze parsea cada formato y separa registros aceptados, rechazados y tombstones. Silver construye un histórico canónico de eventos de contratación, sin reducirlo prematuramente a una única fila vigente. Después, PySpark resuelve el estado actual y genera Gold con las oportunidades abiertas. DuckDB publica vistas SQL y finalmente se exportan CSV deterministas para Tableau. Esta separación permite repetir una etapa sin reinterpretar las anteriores y mantiene la lógica fuera de la herramienta de visualización.

04 · Trazabilidad y calidad

La calidad debe revelar problemas

No fabricar un informe verde eliminando silenciosamente lo que no encaja.

01

Raw inmutable: bytes y checksum conservan la evidencia.

02

Rechazos observables: cada error mantiene motivo y localización.

03

Historia explícita: revisiones y tombstones siguen en Silver.

04

Gold conservador: sin evidencia de apertura, no se publica.

Una decisión clave es no ocultar los datos problemáticos. Cada rechazo queda contabilizado con su motivo y localización. Los identificadores se derivan de claves oficiales; las revisiones y tombstones permanecen en Silver; y Gold solo publica una oportunidad como abierta cuando existe evidencia suficiente. Por eso, obtener cero oportunidades con los fixtures de prueba no es un fallo: es el comportamiento esperado de una política conservadora. Un informe verde no debe fabricarse filtrando silenciosamente lo que no encaja.

Una ejecución · seed 7 · carga sintética acotada. No es un umbral universal ni mide el pipeline completo.

También comparé motores para la transformación Silver. En el experimento versionado, con una carga sintética de 25.363 entradas Bronze y 22.504 eventos Silver, las tres implementaciones produjeron resultados equivalentes dentro del contrato medido. Polars nativo tardó 0,254 segundos; la referencia Python, 0,617; y el candidato Spark, 10,01 segundos. Esto no demuestra que Polars sea siempre mejor ni que Spark no sea útil. Demuestra algo más defendible: para esta transformación local y este volumen, Polars fue la opción medida más rápida; Spark se reserva para ventanas, joins y Gold, donde su modelo sí aporta.

06 · Resultado demostrable

Una cadena reproducible, desde el fichero oficial hasta el análisis

6fronteras persistentes o publicadas: Raw, Bronze, Silver, Gold, DuckDB y CSV
9.454códigos del vocabulario oficial CPV medidos
5exportaciones CSV preparadas para el montaje en Tableau

CLI + Parquet + contratos + manifests + fixtures locales sin dependencia de red.

El resultado es una cadena ejecutable desde CLI y probada con fixtures locales, sin red: Raw, Bronze y Silver; estado vigente y Gold en Parquet; vistas DuckDB; y cinco exportaciones CSV preparadas para Tableau. Además, el proyecto incluye la referencia CPV completa, con 9.454 códigos medidos, y una dimensión DIR3 construida desde seis ámbitos oficiales. Los manifests registran versiones, conteos y métricas para poder relacionar cada producto con la ejecución que lo generó.

07 · Límites y conclusión

Un prototipo defendible, no una plataforma en producción

Incremental completo + Airflow
Contratos menores + semántica
Cloud + operación multi-host

La utilidad analítica empieza por una base reproducible, trazable y honesta sobre sus límites.

El prototipo no es una plataforma en producción. La completitud incremental de ventanas, Airflow, los contratos menores, el enriquecimiento semántico y el despliegue cloud quedan como trabajo futuro. La conclusión es que la utilidad analítica depende primero de una base reproducible y trazable. Este TFM aporta esa base: integra fuentes heterogéneas, conserva la historia y convierte datos oficiales en productos analíticos sin perder la evidencia necesaria para defender cada resultado.
